
# Where a workflow is, and what's next

Every framework skill uses this one rule: at its entry, before its opening, and when the leader says "continue my workflow". Where code can run, the `framework-state` script applies it and returns the state; this file is the rule and its written fallback. It is the same, byte for byte, in every skill that carries it. Two parts are kept in their own files, read only when they apply: `location.md` (every platform but Claude Code and Codex) and `routing-rare.md` (the rare cases named under the state table).

## What it reads

- **The workflow's folder,** current files only: `requirements.md`, `deconstruct-in-progress.md`, `design-plan.md`, `build-record.md`, `test-results.md`. To spot an earlier version (`routing-rare.md`, *Earlier versions*) it also looks for `design-spec.md`, and checks only whether `run-guide.md` or an old run log is in the folder. Never `history/`, except whether a `history/set-aside-*/` folder exists and, for the live test below, the newest set-aside build record.
- **The Workflow node,** where there's a registry: `status` and `big_change`.
- **With no registry:** `big_change` in the frontmatter of `requirements.md`, and the "Live since" line at the top of `build-record.md`.
- **The framework folder** (`framework/` in the working folder), for "continue my workflow" only: its workflow folders (and, where there's a registry, their nodes), whether `analyze-in-progress.md` is there, and whether there are backlog candidates (the registry's `backlog` nodes, or, with no registry, `backlog.md`).

## Terms

- **Live:** with a registry, the node's `status` is `in-production`. With no registry, the build record's top section says "Live since YYYY-MM-DD"; or, while a redo is pending or being rebuilt, the newest build record in `history/set-aside-*/` says so.
- **Plan revision:** the highest task `rev` in `design-plan.md`. It is worked out, never stored.
- **The last round:** the round in `test-results.md`; its number is `round`. With no results file, the last round is 0.
- **A Build close after the last round:** the build record's `last_close_after_round` is at or above the last round's number. (A round still in progress when Build closed is set aside before this is read: "A round left behind", below.)
- **An unlogged change request:** an entry under `change_requests` in `build-record.md` or `test-results.md` whose `id` isn't in the plan's `changes:` log. A request whose only task is `SCH` (a schedule-only request) doesn't count. An entry with no `id` can't be read: routing stops and falls back to reading the files by hand.
- **Built and saved:** the record shows the task built, with `Saved: yes`. Two cases count as built: a task Build finished with a known miss (`Built, misses [line]`: after Build's first close, its check failed because a requirement line can't be met, and Test settles the line), and the `SCH` task recorded with `schedule: safety-incomplete`.
- **An earlier version:** `routing-rare.md`, *Earlier versions*.

## The states

Check these in order. The first that matches is the state.

| # | State | What shows it | Owner |
|---|---|---|---|
| 0 | Not a framework workflow, or retired | The node is `retired`; or the node is `in-production` and the workflow has no folder (running work Analyze recorded) | None: state 0's line, then stop. Two exceptions: "change my workflow" on a retired workflow goes to Design, and Deconstruct by name ("run the deconstruct skill on [workflow]") on running work goes to Deconstruct (both in `routing-rare.md`) |
| 1 | Earlier version | A file in an earlier version's format | The step that writes the earliest such file |
| 2 | Redo pending | `big_change` is set | Deconstruct |
| 3 | Requirements needed | No `requirements.md`, or a `deconstruct-in-progress.md` | Deconstruct; Analyze when the leader has no workflow in mind yet |
| 4 | Plan needed | No `design-plan.md`; or the requirements' `revision` is above the plan's `requirements_revision`, not counting revisions marked `plan_unaffected`; or an unlogged change request | Design |
| 5 | Plan to approve | The plan isn't `approved: true` | Design |
| 6 | Build needed | No `build-record.md`; or a task not built and saved, other than one waiting on an unanswered open item; or a task whose `rev` is above its built `rev` in the record; or the record's `plan_revision` isn't set or isn't the current plan revision, unless a task waits on an unanswered open item; or `direct_edit: undo` in the results with no Build close after that round; or the last round is `not-ready`, has an Issues row at Level `build`, and has no Build close after it | Build (after a Not ready round, in fix mode) |
| 7 | Waiting on an open item | Every task that can be built is built and saved, and at least one waits on an unanswered open item | Design, to answer the item |
| 8 | Test needed | No `test-results.md`; or a round `in-progress`; or a Build close after the last round; or the last round is `not-ready` with nothing in it for Build (no Issues row at Level `build`, no `direct_edit: undo`) | Test |
| 9 | Waiting on access | The last round is `waiting-on-access` | Test (it gives the connection's steps, then checks again) |
| 10 | Ready to go live | The last round is `ready` for the current plan revision, with `go_live: pending` | Test |
| 11 | Live | Live, and nothing above matched | Test, for a re-check |

**Rare cases are in `routing-rare.md`** (in this folder). Read it when one applies, and not otherwise: a round left behind (Test meets a round `in-progress` that an older plan revision or a Build close left open); a retired workflow brought back ("change my workflow" on a retired workflow); running work brought in (state 0's `in-production` work with no folder); an earlier version (state 1, and whenever this rule is applied by hand, to tell an earlier version's format); a cloud session.

## What each step accepts

- **Analyze:** state 3 when the leader has no workflow in mind yet; its own progress file; and, by name, at any time, to find more workflows.
- **Deconstruct:** states 2 and 3; and state 0's running work, by name (or by "change my workflow", when the leader says that here), which it takes as a new workflow (`routing-rare.md`). By name, a re-run of the requirements while there is no `build-record.md` (states 4 to 6): the plan is kept, and the raised `revision` sends Design to update it.
- **Design:** states 4, 5 and 7. By name, re-planning while there is no `build-record.md` (it updates the plan in place). "Change my workflow" in any state from 4 on (in state 4 with no plan yet, Design runs its normal flow), and on a retired workflow in state 0, which it brings back (`routing-rare.md`). A change to the schedule alone, by name, in any state from 4 on.
- **Build:** state 6; after a Not ready round with Issues rows at Level `build`, in fix mode.
- **Test:** states 8 to 11. In state 10, when the workflow is already live (a go-live that was interrupted), Test finishes the remaining go-live steps without asking again. In state 11, "test the workflow I built" opens a re-check round.
- **State 1:** the owner asks N-B44 first when the workflow is live or was built, then starts fresh (`routing-rare.md`, *Earlier versions*); any other step says N-T22 with the owner's start phrase, and nothing else.

## When this step isn't the owner

Say in one line where the workflow is and which step is next, with that step's start phrase and the location, then stop. That line is the whole message: nothing after it, and nothing before it but, where it fits, the routing lead-in (below). Use these lines where they apply:

- **State 0, running work** (the running-work message): "This workflow already runs outside the framework. To bring it in, say 'run the deconstruct skill on [workflow]. My files are in [location].' Deconstruct pins down its goal, what it must get right, its rules and a few practice runs; until the new version is built and installed, keep running it as it is." On Claude Code and Codex, in full: "This workflow already runs outside the framework. To bring it in, say 'run the deconstruct skill on [workflow].' Deconstruct pins down its goal, what it must get right, its rules and a few practice runs; until the new version is built and installed, keep running it as it is." Only [workflow] and [location] are filled: it opens "This workflow…", never with the workflow's name, and keeps its three sentences as they are. The location is the working folder (on Claude Code and Codex, the framework folder). A step other than Deconstruct that receives "change my workflow" on running work says the bring-in line instead, which gives the same phrase in N-F2's new-chat form: "To bring [workflow] into the framework, start Deconstruct in a new chat with: 'run the deconstruct skill on [workflow]. My files are in [location].'" (on Claude Code and Codex, "To bring [workflow] into the framework, start Deconstruct in a new session in this project with: 'run the deconstruct skill on [workflow].'"). On Claude Code, when "change my workflow" about running work is the first thing the leader asked in this chat (no work has started here), start Deconstruct directly in this session instead (on Codex, the bring-in line as above), with no text first but, if you choose, the routing lead-in (below) said exactly (never a line of your own in its place, such as one saying you are checking where the workflow stands or bringing it into the framework), as "Continue my workflow" step 3 does: the skill call says "run the deconstruct skill on [workflow]", followed by the leader's own words, and Deconstruct takes it as that request, opening with its question on how the work runs today. The bring-in line stays for every other platform, and for Claude Code and Codex once work has started in the chat.
- **State 0, retired** (the retired line): "This workflow is retired. To bring it back, say 'change my workflow. My files are in [location].'" Said word for word, with nothing before it: a retired workflow has no next step, so no reason or lead-in comes first.
- **State 1** (N-T22): "This was made with an earlier version of the framework. Start it again with '[start phrase]. My files are in [location].'"
- **State 7** (the open-item line): "[The waiting tasks, in plain words] wait for [the open item]. To answer it, say 'run the design skill. My files are in [location].'" With one waiting task: "[The waiting task, in plain words] waits for [the open item]. To answer it, say 'run the design skill. My files are in [location].'"
- **State 11, on "continue my workflow", or when Design is started by name** (N-T19): "This workflow is live. To change it, say 'change my workflow. My files are in [location].' To re-check it, say 'test the workflow I built. My files are in [location].'"
- **Any other state:** the step's own not-owner line where its SKILL.md gives one (Test, states 2 to 6: N-T25); otherwise two sentences and nothing else. First, where the workflow is: the routing lead-in (below) where the state has a phrase, or else one sentence of model wording that names the workflow and says where it is in plain words. Then the sentence that sends the leader on, which is N-F2 in its platform form, word for word, with the owner step's name and its start phrase, never model wording: "Start [step] in a new chat. Add your [storage service] to it, then say '[start phrase]. My files are in [location].'" On Claude Code and Codex: "Start [step] in a new session in this project and say '[start phrase].'" On Claude desktop, with the files in a local folder: "Start [step] in a new chat with your working folder selected: '[start phrase]. My files are in [location].'" On Microsoft 365: "Start [step] in a new Cowork chat with: '[start phrase]. My files are in OneDrive, in ai-workspace/framework/[workflow-slug].'" (before the workflow has a folder, "…My files are in OneDrive, in ai-workspace.'").

| Step | Start phrase |
|---|---|
| Analyze | "run the analyze skill" |
| Deconstruct | "run the deconstruct skill" ("…on [workflow]" when naming one) |
| Design | "run the design skill", or "change my workflow: [what changed]" |
| Build | "run the build skill" |
| Test | "test the workflow I built" |

Each is followed by "My files are in [location]." What [location] is on the web, on Claude desktop and on Microsoft 365, and how these lines read there: `location.md`. A step accepts either from the leader: a workflow's folder names the workflow; with only the working folder, the step finds the workflow in its `framework/` folder: the one the leader named, or else as "Continue my workflow" step 1 finds it. Each step runs in a new chat (on Claude Code and Codex, a new session in this project). On Claude Code and Codex the workspace is the working folder, so a start phrase carries no location: "run the design skill.", said in a new session in this project. Every line that gives '[start phrase]. My files are in [location].' gives '[start phrase].' there, its "in a new session" reads "in a new session in this project" (N-F2's form), and N-F3's [location] is "this folder". Nothing there says to work outside a Project: the project is the working folder. A step started with no location finds the workflow as it does with only the working folder. A cloud session: `routing-rare.md`. Every start phrase is said word for word, as the table gives it: never reworded or shortened ("Run Analyze" is wrong); a capital letter at the start of a sentence is fine.

**The routing lead-in** (N-F23). Optionally, one sentence may say why the next step is next, exactly: "[Workflow] [state], so the next step is [step]." [Workflow] is the workflow's name, [step] the next step's name, and [state] one of these plain phrases, by the state found:

| [state] | When |
|---|---|
| "has its requirements" | States 4 and 5: Design is next |
| "has its plan" | State 6: Build is next |
| "is built" | States 8 to 10: Test is next |
| "already runs" | State 0, running work: Deconstruct is next |
| "is in your backlog" | No workflow folder that isn't retired, and a backlog ("Continue my workflow" step 1): Deconstruct is next. [Workflow] is the one the leader named; otherwise the first backlog workflow, in the order Deconstruct's backlog choice lists them |
| "is live" | State 11, when the leader asked to change it (Design) or re-check it (Test) |
| "is retired" | State 0, retired, only when the leader asked to change it (Design brings it back) |

It comes only as the single sentence before a fixed routing line that names the next step (the running-work message, the bring-in line, N-F21, and N-F2 in the "any other state" reply above), or before starting another step's skill directly: on Claude Code that is the hand-off, the lead-in and then the skill call, with no other text. It is never required, and never joined to any other text. Never before N-F22 ("There's nothing to continue yet…"), which already carries its reason (only N-F24, below, may come before it); never before the retired line, which is said word for word with nothing before it, since a retired workflow has no next step; never before N-T19, N-T22, the open-item line or N-F9; and never in a state with no phrase above.

**Before N-F22** (N-F24). When the registry has no Workflow nodes at all, one sentence may come before N-F22, exactly: "Your registry has no workflows yet, so the next step is Analyze." It is optional, its own paragraph, and the only sentence ever allowed before N-F22: no other reason or lead-in comes before it, and nothing comes after N-F22. With no registry, or a registry that has Workflow nodes (running or retired work), it isn't said.

## "Continue my workflow"

Any framework skill may receive it. On the web with no location given, first find the working folder: a folder named ai-workspace; else a folder holding `registry/SCHEMA.md` or `framework/`, taken as the working folder once the leader confirms it in one line; else, with none, N-F1, the storage question, in full (Analyze and Deconstruct give it from their own files, with what follows it there; in Design, Build and Test it is this): "Where should your working folder go? It holds your AI Registry, your workflows and your knowledge graph. Say 'go ahead' and I'll make a private folder called ai-workspace in your [storage service], or tell me the name of one you already have. To keep it somewhere else, such as Google Drive, OneDrive or Box, add it to this chat from the prompt box first. The connection reaches your whole drive, but I'll only read and save inside that folder, and never share or delete anything. Run each step of the framework in a new chat that isn't inside one of your [Claude / ChatGPT] Projects." In Design, Build and Test, a folder the leader names is the working folder; on 'go ahead', make the folder, which then holds nothing to continue (below).

**Nothing to continue: check this first.** When the leader named no workflow, and the framework folder has no workflow folder that isn't retired, no backlog candidates (the registry's `backlog` nodes; `backlog.md` only where there's no registry) and no `analyze-in-progress.md`, there is nothing to continue. Whatever else the working folder holds, the whole message is this:

- **Optionally, first,** only when there is a registry with no Workflow nodes at all, N-F24 as its own paragraph: "Your registry has no workflows yet, so the next step is Analyze."
- **Then N-F22,** in its platform form, in full. On the web, Claude desktop and Microsoft 365 ([location] is the working folder): "There's nothing to continue yet. To find workflows worth building, say 'run the analyze skill. My files are in [location].'" On Claude Code and Codex: "There's nothing to continue yet. To find workflows worth building, say 'run the analyze skill.'"

Nothing else, then stop: no account of what the folder holds, no explanation of Analyze or the framework, no question and no offer to start, and no other reason or lead-in (N-F22 carries its own reason). Every step says it, Analyze included. Otherwise, go on:

1. **Find the workflow.** If the leader named one, that one. Otherwise, if `analyze-in-progress.md` is in the framework folder: Analyze owns it when no workflow that isn't retired has a folder; when some do, ask N-F9 with the unfinished Analyze session listed beside them, whether there is one of them or several. Otherwise, among the workflows that have a folder and aren't retired: the only one in progress, by the states above (any state but 11: not yet live, or live and partway through a change, a fix or a redo); or, when none is in progress and there's only one, that one (state 11 then says N-T19); otherwise ask (N-F9): "Which workflow should we pick up: [Name] ([where it is, in plain words]), [Name] ([where it is])?" With exactly two, and no unfinished Analyze session: "Which workflow should we pick up: [Name] ([where it is, in plain words]) or [Name] ([where it is])?" With an unfinished Analyze session, the question ends "…, or your unfinished Analyze session?", and picking it gives it to Analyze. Backlog candidates with no folder don't count, and neither do retired workflows: with no folder for a workflow that isn't retired, but a backlog, Deconstruct owns it (its backlog choice does the picking): give its start phrase with the location as step 3 says; with neither, it's the nothing-to-continue case above. If the files aren't there, ask (N-F3a): "I can't find the files for [workflow] in [where I looked]. Where are they?" On Claude desktop, or on Microsoft 365 when Cowork can't read the drive, a chat that can't read any framework files asks N-F13 instead (`location.md`), since it couldn't open a path the leader gave.
2. **Work out the state.**
3. **If this skill owns it, carry on,** with a resume line in place of the opening. Otherwise give the owner's start phrase with the location, to say in a new chat, and stop. In state 11, say N-T19 rather than starting a re-check. **When "continue my workflow" is the first thing the leader asked in this chat** (no work has started here), the owner starts in this chat: in place of a new-chat line (the model-wording line, or Deconstruct's phrase for a backlog), say N-F21, exactly, "[Step] picks this up from here. Say '[start phrase]. My files are in [location].' in this chat to start it." (on Claude Code and Codex, "[Step] picks this up from here. Say '[start phrase].' in this chat to start it."), and stop; never "start a new session" or "open a new chat". On Claude Code, where the owner's skill can be started directly in this session, start it instead of saying N-F21 (on Codex, N-F21 as above), with no text first but, if you choose, the routing lead-in (above): the owner then gives its own resume line or opening. N-F21 is for every other platform, and for Claude Code and Codex when the owner's skill can't be started there. The fixed lines (state 0's lines, N-T22, the open-item line, N-T19, N-F9) are said as they are: on Claude Code and Codex a line that sends no one to a new session or chat ("To answer it, say…") gets none added.

## The order at every entry, before the opening

1. **The wrong place** (every step but Analyze): this chat is inside the workflow's own place (its context files present, no framework files). Say N-F7 and stop: "This chat is inside your workflow's [Project / folder], where it runs, so I'll keep the framework out of it. Open a new chat outside it and say '[start phrase]. My files are in [location].'" Claude desktop: "This chat has your workflow's folder selected, where it runs, so I'll keep the framework out of it. Open a new chat with your working folder selected and say '[start phrase]. My files are in [location].'" On Claude Code and Codex, the workflow's place is the workspace it's installed in: when the workflow's skill or agent is installed in this workspace (`.claude/skills/[workflow]/` or `.claude/agents/` on Claude Code, Codex's skills folder) and the workspace has no `framework/` folder, this is the wrong place, not a missing location, so it comes before the location: say N-F7's Claude Code and Codex form, "This session is inside the workspace where your workflow runs, so I'll keep the framework out of it. Start a new session in your working folder and say '[start phrase].'", and stop. Never ask where the files are.
2. **The location:** on Claude Code and Codex the workspace is the working folder (above): take the workflow from the start phrase, or find it. On every other platform, read `location.md` first: the check for a drive this chat can save to (N-F16), where the files are, and what to say when this chat can't read them (N-F13). The opening confirms the location in one line (N-F3). Nothing is read, saved or asked until the files can be read.
3. **The state,** by the table. In state 1, when this step is the owner and the workflow is live or was built (the node is `in-production`, or skills or agents are linked, or the folder has results, a run guide or an old run log), ask first (N-B44): "[Workflow] was made with an earlier version of the framework, so I'll set its old files aside and start fresh. If it runs on a schedule, pause it first: [steps]. Say 'done' when it's paused, or 'no schedule'." It isn't asked again in the same chat once answered.
4. **Is it this step's?** If not, the line above, and stop.
5. **This step's own entry checks,** then its opening, or a resume line. When an entry check asks the leader something before the opening, its message starts with one line that names this step and the workflow and confirms the location (N-F3's promise clause), so a new chat never opens on a bare question; the opening then doesn't repeat that line.

**Scripted lines are said in full.** A line these rules or this step give in quotes to be said exactly is said in full: every sentence, in its order, with only its [brackets] filled, never dropped, merged, shortened or paraphrased, on every platform.
