# The review

Read at the start of Part 4, before writing the review, and whenever the review is shown again. The consequential points, the approval question and the close are in SKILL.md (*Phase 4*).

**The review** opens with one line *(your words)* saying this is the plan in brief and where the full plan is (the location filled in), and covers the points below, in plain words, with no requirement or task IDs. Items 1 to 5 are the plan's `## Summary`, said as the file has it. **Each main choice carries its why:** what it's built from (a skill or an agent, reused or new), how it runs (you start it, or it runs on its own), how the output reaches the leader, and where they check it each get one plain line of why, in terms of their requirements ("one input and rules that settle each decision, so a fixed set of steps is more reliable"; "you send every email yourself, so it only drafts"), never a framework term. The plan's `## Summary` carries the same whys. Say only what the plan and the requirements hold: add no detail, name or figure that neither states, and claim nothing about your own work that the files don't show.

1. **How it will run:** where it runs, how the leader starts it, whether it runs with or without them, and how the output reaches them (the plan's `Delivered as:`). Never the level's name (Deterministic, Guided, Autonomous) or a paragraph on how much it decides: the level is in the plan file only. When the plan has `fixed (regulation)`, `fixed (policy)` or `fixed (your judgment)` steps, add one plain line saying those steps are kept exactly as they are, without naming a level: "The steps your requirements fix are kept exactly as they are." *(your words)* For a `Path: none` plan with planned steps, a `domains` plan, or regulated work planned as Autonomous, first read `variants.md`, *The review*: its lines go here.
2. **The skills it reuses, builds or adds to,** one line each: what it does and what it never does. "Skill" means "you start it and it follows your steps"; "agent" means "it works out its own steps and can run without you". Use each word only where that is true of this plan. Where it isn't, use the form that is, said exactly: an agent that runs with the leader, "it works out [the part it decides], and you start it and read what it gives back"; an agent that follows the steps you planned, "it follows the steps in this plan and works out [the part it decides] on its own"; a skill whose steps you planned (`Path: none`), "you start it and it follows the steps in this plan".
3. **What it can read and change,** one line per connection, naming any change that can't be undone and where it asks first. State a limit as the rule the workflow keeps, never as a fact about a place you haven't seen.
4. **How it's checked,** in one or two short sentences: the practice runs by kind (the typical case, and the hard cases by name), and any practice input you added for a risk. Never every check or rule again: the leader has just approved them, and the plan file lists them.
5. **Keeping it working,** in one line: each run flags anything it wasn't designed for (plus the re-check line, and the time-saved line where a known Baseline gives one). For a scheduled workflow: Build prepares the schedule but never switches it on, and the leader runs it once by hand before its schedule goes on, and again after any change to it while it's live.
6. **What the checks fixed:** each fix the self-check and the plan check made, named in the leader's terms as what changed in the plan (the part, the rule or the step, in plain words), in one line of model wording *(your words)*: "I checked the plan against your requirements and fixed two things: [what changed, in a few words] and [what changed]." Never your own working terms ("build notes", "my note", "the blueprint"). With nothing fixed, one short clause saying so. Never a count without the fixes, and never "they're listed in the plan" (nothing of the check is saved there).
7. **Gaps,** only when the coverage check (`self-test-checklist.md`) found one it couldn't close: one line each, saying what isn't covered and what waits for it. With no gap, nothing.
8. **Anything assumed:** every assumption and default from over the cap, each easy to change.
9. **Open items,** each as one statement of what is still unknown and what waits for it, never a question, with no label or heading: "[Whether, which or who: the unknown] is still open, so [the parts that wait, in plain words] wait[s] for it." The review has no question mark anywhere before its closing ask; an open item is asked when the leader comes back for it.

It ends: **Ask:** "What would you change or clarify?" That is the message's one question, its last line: the approval question (SKILL.md, *Approval*) never goes in the same message, and nothing before it asks anything.

**Changes.** A correction is saved as it's given (SKILL.md, *Saving and resuming*): it updates the plan (its `## Summary` too), runs the self-check, the plan check and the coverage check, and shows the review again; the plan stays `approved: false`.

- Lowering the level is always allowed. Raising it needs the evidence and the limits to support it; otherwise give the reason in one line (D7 when a limit is involved). The same holds for a reply to B54.
- A change that creates a Part 3 question (`questions.md`) asks it before the review is shown again. It isn't counted against the cap, and safety questions are always asked.
- A raise the evidence doesn't support, insisted on: keep the plan, record the wish in the Approach as "the leader's recorded wish", say in one line it can be revisited after real runs with "change my workflow. My files are in [location].", and move on to approval.
