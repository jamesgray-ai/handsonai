# Drafting the plan

Read at the start of Part 2, with `plan-template.md`, after Part 2's two lines are said (SKILL.md, *Phase 2*). Draft with no text to the leader.

1. **Read the requirements** by `Method preference` and `## Path`:
   - `same way every time`: the steps and their order are a limit. A flexible step's method is yours to choose; a fixed step stays as written.
   - `some of each`: fixed steps are designed as steps; a person's step the leader didn't pick stays a flexible step with its role. Each `- The AI plans this part` is one part the AI works out each time, with a plan ID after the step it follows (`Step 2a`; `Step 0a` when first). Split a part into planned steps (`Step 2a`, `Step 2b`…) only when a set path does its job better, and say so in one line in the review. Context `Used By`, data readiness and checkpoints anchor to the part.
   - `AI works it out each time` (`Path: none`): propose the breakdown. Use `decomposition: domains` (read `references/capability-domains.md`) when your breakdown makes every part Autonomous and nothing is fixed; otherwise plan your own steps (`Step Pa`, `Step Pb`…) and say B54 (`variants.md`) in the review. An order the leader insisted on (an `Always` R line, "It always [does this] before [that]") is kept on this route too, `domains` included: the plan honours it as the rule it is, carried into the blueprint of the part it governs and checked in that part's *Done when*, and never drops it because no step is fixed. With such a rule, `domains`' variant line isn't said (`variants.md`).
   - On every route, read the rest as `plan-template.md` section 1 says: what the requirements record (how runs start, what it remembers, a write's place, the flag line, the Fallback, `Policy check:`) is read there, never asked. A file Deconstruct writes now has `Path: none`, so the Path may hold little more than the `Method preference` line; read it the same way. An 11.0 file (with `## Output`) is read in full: its Output, each check's `· from:`, and scenarios Test writes, which have no `inputs/` file yet and need none. A 10.x file reads as before. Never read `standing-rules.md`.
   - **How the output is delivered:** the plan's `Delivered as:` line, drafted from the Output and the writes (`plan-template.md` section 1); asked only when nothing settles it, and never adding a write the requirements don't hold: a write is added only on the leader's yes to N-32 (`questions.md`, *A delivery that needs a write*); without it, the output is shown in the chat.
2. **Check platform facts** as `references/platform-facts.md` says. A lookup never blocks Design; an option that couldn't be verified goes into Deferred to Build, for Build to confirm (`plan-template.md`, Integration Options).
3. **Set how much it decides on its own,** step by step and part by part: the least that does the job, judged by what decides the next step.
   - **Human:** a person does it. **Deterministic:** instructions; anything the AI writes never changes what happens next (a branch on a value the AI didn't judge stays Deterministic). **Guided:** the AI's judgment, by the leader's criteria, decides what happens next. **Autonomous:** a goal; the AI plans its own steps until it's met.
   - The workflow's level is the highest any AI step reaches. Writing, summarising, a person's review and the number of agents never raise it. A fixed step can be Guided, never Autonomous. The leader's limits cap the level, and the preference never raises it.
   - **Regulated work:** any level that keeps every rule and checkpoint that names the law as its reason (and, in an older file, every step the regulation fixes), and the decisions a person must make. Autonomous regulated work gets D3′ (`variants.md`) in the review and a per-run record (a required Traceability row in Constraint Conformance). With the regime `Not sure — to check` and an Autonomous plan, Part 3 asks D4′.
   - **Keep it simple:** one agent before several, each split naming its reason (protecting context, parallel coverage, specialisation, a security boundary); a stopping condition and a cap on every loop, with an actions-per-run cap for anything unattended; a person before high-risk or irreversible actions.
   - **The pattern:** the Autonomy Summary names it from the playbook catalogue in `plan-template.md` and cites both the playbook page and its primary source, fetched by URL where the platform can. Never invent a source: a pattern you can't attribute is described without one.
4. **How it runs** (`plan-template.md` section 2): the mechanism (`Agent` when it decides its path at runtime, uses tools on its own judgment, or runs unattended; otherwise `Skill`), involvement, packaging, `platform_mode`, connections, the run log and any schedule, all decided by you and never asked. On Claude Code and Claude, read `references/orchestrator-on-primary-loop.md` before planning agents or the orchestrator: there the orchestrator skill is always S1, with its blueprint and its own task, whatever the mechanism, and on Claude worker agents run only in Cowork, never in a chat on the web or desktop. How runs start, schedules and Microsoft 365's two build places: `plan-template.md`, section 2.
5. **Safety** (`plan-template.md` section 3): the four questions; every write classed by the floor, with the checkpoint before it; each write checked against what the connection can do (N-14 if it can't); Constraint Conformance by `P` ID.
6. **Reuse:** look for the leader's skills (linked from the registry's other workflows, or installed on the platform). Where one covers a part, Part 3 asks N-13; building new needs no question. A part that uses a skill from another plugin (the reused skill lives in one, or the Output's Voice line names a guide that is a skill) gets the blueprint's `Uses skills from:` line, filled when you draft and again when N-13 is answered. On Microsoft 365, an agent takes no skill, so reuse is offered only for a skills-only plan.
7. **Rulings after a set-aside:** when `history/set-aside-*/` exists, read the newest set-aside build record's rulings and carry into the blueprints those that still apply (`updating-the-plan.md`, *Rulings*).
8. **Blueprints, tasks and risk inputs** (`plan-template.md`). Write at most two risk inputs, for risks no input covers, straight after the plan's write.
9. **The self-check, the plan check, then the coverage check** (`references/self-test-checklist.md`): fix what fails, and keep a note of each fix for the review (it's named there, never saved in the plan). The plan check is narrow and independent: on Claude Code a fresh-context subagent, everywhere else (Codex included) a deliberate second pass as a stranger would read it; it reports only gaps that would break a requirement, a rule or checkpoint, safety or buildability. A gap you can't fix becomes a Part 3 question or an open item. Both run again after Part 3, after any change in the review, and at every update.
10. **Save the draft** with `approved: false`, its `## Summary` written, the questions still to ask at the top of Open items, marked "to ask".
11. **When anything is left to ask,** read `questions.md` now, with no text: Part 3's signpost and its first question then go in one message.
