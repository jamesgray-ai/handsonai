# Changing a workflow

Read when the leader says "change my workflow" in any form: a bare phrase, a phrase with the change after a colon, on a retired workflow, on running work, or asking to reinstall the workflow or bring it back. Section names in italics are SKILL.md's.

## What Design takes

| Entry | What Design does |
|---|---|
| "Change my workflow", any state from 4 on | *"Change my workflow"*, below. In state 4 with no plan, the full flow; in state 5, the change goes into the draft |
| "Change my workflow" on a retired workflow (state 0) | Bring it back: set the node's `status` to `under-development`, say so in one line, then *"Change my workflow"* with the put-back (`updating-the-plan.md`). With no build record, work the state out again from the files: from state 4 on, as usual; otherwise routing's line for the owner (Deconstruct's phrase when there are no requirements yet) |
| "Change my workflow" on running work Analyze recorded (state 0: `in-production`, no workflow folder) | Not Design's. On Claude Code, when it's the first thing asked in this chat, start Deconstruct directly in this session, with no text first but, if you choose, the routing lead-in (`routing.md`). Otherwise (Codex included) the bring-in line from `routing.md`, with the working folder as the location, in N-F2's platform form (on Microsoft 365, "…My files are in OneDrive, in ai-workspace.'"), then stop. That line is the whole reply: nothing before it but, if you choose, the routing lead-in (no opening, no line on what Design covers or which step takes "change my workflow") and nothing after it. Never the running-work message |
| "Change my workflow" asking to reinstall the workflow or bring it back, any state from 4 on | The same put-back, with no `status` to change |

## "Change my workflow"

After the wrong-place check, routing (states 0 to 3 aren't Design's, except a retired workflow, brought back first) and *Design's own entry checks* (the requirements check runs here too, before any question about the change):

1. **Direct edits first,** only when something is built: the build record shows a task built and saved, or an installed part. In state 4 or 5 with no build record, or a record with nothing built yet, go straight on. Fingerprints decide only what can be compared: compare each installed skill and agent, and the runtime copies of the context files, with the record's fingerprints where you can read them, silently, with no text about it before the opening. An installed part with no fingerprint (an agent Agent Builder made) counts as one that can't be read. Where any can't be read, **Ask:** "Have you edited the workflow's instructions or its files directly since it was built?" (N-E1; only the runtime context copies unreadable: **Ask:** "Have you edited the files your workflow reads ([the files, in plain words]) directly since it was built?"; an agent Agent Builder made on Microsoft 365: **Ask:** "Apart from pasting the prompts I wrote, have you changed [Agent] in Agent Builder, or its Knowledge, since it was made?"). On a yes, say "Paste [the instructions / the file] as [they are / it is] now, so I can match your requirements and plan to [them / it]. [How to copy it out on this platform.]" Then, for an edit found:
   - **An edit Design already declined** (its text matches the edited text saved in the file the `what` of a `changes:` entry names, an entry with source `direct edit` and a `declined:` outcome): **Ask:** "That edit changes [the fixed step, in plain words], which your [rules require / policy requires], so it can't be kept. Shall I put back the built version?" (N-E2; [the fixed step] is also how a line a law requires is named, in plain words.) A yes logs the put-back (`updating-the-plan.md`). On a no, say (N-E2) "Then I'll leave it as it is. While that edit is installed, I can't [test / build / change] [workflow]. When you want the built version back, say '[this step's start phrase]. My files are in [location].'" and stop, changing nothing.
   - **Any other edit:** **Ask:** "I'll record that as a change so your requirements and plan match. OK, or should I put back the built version?" (N-E2) Keep is the recommended, easy default.
2. **A bare "change my workflow":** first one line (model wording) naming Design and the workflow, with N-F3's promise clause and its platform clause (SKILL.md, *The opening*, item 2), unless an entry check already said it; then **Ask:** "What should change? If a real run showed it, paste that input too." (N-27, *your words*) After a direct edit kept in item 1, ask instead: **Ask:** "What else should change, if anything? If a real run showed it, paste that input too." (N-27, *your words*) Every other update's first line carries the same (`updating-the-plan.md`, section 1, step 1).
3. Then `references/updating-the-plan.md`: small or big, the put-back, a real failure offered as a practice input, platform or mechanism changes.

A small change is announced, before anything changes, with: **Ask:** "That's a small change: I'll update your requirements and plan to include [the change][, then you approve it]. Ready?" *(your words)* (N-22; the bracket only when the change alters a consequential point). Updates run with no signposts.
