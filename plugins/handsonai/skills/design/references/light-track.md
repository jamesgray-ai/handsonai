# The light track

Read when the requirements say `track: light`, before drafting the plan, and when Build reports a track switch.

`track: light` in the requirements: the same four parts, file and format. Part 3 asks at most three questions. The review is one message: the main choices (where and how it runs, how much it decides on its own, what it reads and changes), the tasks in plain words, anything assumed or defaulted, the plan check line and any open items; with no consequential points it ends with "Do you approve the plan? Build won't start until you do." instead of "What would you change or clarify?", and a correction goes through `review.md`'s *Changes*; with points, the points and N-6 as on the full track. Sections stay short (Integration Options and Data Readiness are often one line). A risk input takes one of the three places Test runs where one is free; when Deconstruct already saved three (or an instruction-carrying paste on top), it goes in as Test's cap allows (`test/SKILL.md`, *The practice set*), never in place of one the leader confirmed.

**The automatic switch,** a safety net kept on purpose: Deconstruct sets `track:` from the risk signs it heard, so a risk that shows up later (in the writes the plan needs, or in a track switch Build reports) is caught here, and Build and Test keep the same catch at their steps. When a light workflow shows a sign of risk (a change that can't be undone, a write to a shared or live system, running without the leader, regulation, confidential or outside content), judged on the writes the workflow needs (never on access the plan check removes) and by the floor in `plan-template.md` (a draft no one sees until a person sends it, or a new file only the leader sees, is no sign: its clause "sends, posts or changes something other people see" is for a send, a post or a change to something other people see, never for a draft or file only the leader sees), in Part 3 (on an update, such as a track switch Build reports, first among the update's own questions), straight before the draft or proposal it leads to (`SKILL.md`, step 4), say N-L2 (model wording ending with its promise clause: "This [changes something that can't be undone / sends, posts or changes something other people see / runs without you / is regulated / reads confidential details or content from outside your team], so it needs a few more safety answers."), then the next action, and write `track: full` to the requirements (no `revision` raise). Say N-L2 only when a safety answer will then be asked or drafted; when the file already holds every one the plan needs, write `track: full` and say nothing about it. From then on the full track applies. Any safety answer the plan then needs takes `SKILL.md` step 4's one path (the security limits drafted, the Fallback proposed), in Part 3 or first among an update's questions, recorded with N-15 (`questions.md`), raising `revision`; never a question you word yourself, and nothing else is asked as a block. When the switch comes from confidential or outside content and the Security section has no table for a category it trips (it opens "No sensitivity constraints…": Deconstruct writes that when no test tripped, above a Prohibited actions table the leader kept, or alone when they dropped every line), the security limits for those categories are that missing answer, never settled by that opening: draft them in one message, each in plain words under its category, each kept or dropped, record what's kept in the Security section with the next `P` ID, and remove the opening sentence (`requirement-lines.md`). A category heading with an empty table is answered and never drafted again.
