# Part 2: Scope and a name

Read when Part 2 starts, right after its signpost. On the light track, it's read at the name and description, for the boundary tests, the name's style, the folder and process lines and the law question (asked there with the safety questions); its after-signpost line and the separate name and description messages aren't used. Every quoted line is said exactly; each question is its own message.

Say first: "Next, we'll pin down what starts this workflow and where it ends, then give it a clear name and description."

In a personal-life registry, the personal-life wording replaces the trigger and deliverable confirmation, and the law question is skipped.

## One trigger, one deliverable

Both are prefilled (from the backlog candidate, the cold-entry answer, the leader's document, or, for running work brought in, the answer to how it runs today): play them back and confirm with "Does that match?", never ask them again. For running work brought in, play back the `Runs today` row with them.

Run these tests yourself; never turn them into questions:
- several independent starting points ("when a lead comes in" and "end of each week"): separate workflows;
- someone receives a deliverable midway while the work goes on toward a different output: a workflow boundary;
- parts that run on different schedules, or with long waits between them: likely separate workflows;
- more than about 15 steps: may be several workflows;
- on the Organizational lens, no single accountable owner of the outcome: may be several workflows.

With several, map each (a working name, trigger and deliverable), present the breakdown, confirm the boundaries, and ask which to deconstruct first. Carry on with the chosen one only.

## The name and description

Offer two or three names: a two-to-four-word noun phrase in Title Case, each part of a hyphenated word capitalised ("Follow-Up"; fix a backlog name's casing in the options), clear without context ("Lead Qualification", "Newsletter Distribution"), preferring `[Subject] [Action]` ("Invoice Generation", "Inbox Triage") over verb phrases or vague labels. Ask only which name they want. Confirm the description in the next message, on its own: one sentence in the `naming-workflows` shape (when it starts, what it produces, who receives or acts on it; no targets, no tool names): "After a scoping call, drafts the follow-up email that recaps the call and shares what was discussed, ready for you to review and send."

The confirmed name becomes a kebab-case ID (lowercase, hyphens, no punctuation), unless the workflow already has a Workflow node: then the ID is the node's slug, whatever the name (*A rename keeps the node and its ID*, below). Say: "Everything for this workflow will go in a folder called `[id]`." Every later step uses that ID verbatim.

**The process line.** With a registry and no backlog node (cold entry), say in one line (model wording), right after the folder line, which of the registry's processes the workflow goes under. Where none fits, ask Analyze's no-process question once, word for word, in its own message:

**Ask:** "[Workflow] doesn't fit any of your processes. What would you call the set of related work it belongs to, and which function (the team or role that owns that kind of work) looks after it? Your functions are [the registry's Function names]."
- *Why:* every workflow sits under one process, and the process's owner owns the workflow too.
- *Example:* a bookkeeper might say: "Client Onboarding, and Client Services looks after it."
- *Not sure?* I'll suggest a name from your own words and the function in your registry that fits it best. You can change either later.

A person the leader names, or a function not in the registry, maps to the Function that fits, said in one line ("I'll put it under [Function]."); if none fits, **Ask:** "Shall I add [function] as a new function?", and on a yes the new Function is written at the close.

In a personal-life registry, the question takes the personal words throughout: "routine" for "process", "role" for "function" (and "your roles are" for "your functions are"), "your household" (or "your life" for one person) for "your work"; its parenthetical becomes "(the person in your household who handles that kind of work)", its *Example* is dropped, and the new-function follow-up says "role". The node, and any new Process or Function, is written at the close.

**The first progress save** follows here, once the description is confirmed (SKILL.md, *Pause and resume*).

**A rename keeps the node and its ID.** If the leader renames a workflow that already has a Workflow node (a backlog pick, or running work brought in), the folder stays `[node slug]`: the folder line names that existing ID, not one made from the new name, and only the workflow's name and description change. No new node is made, and the progress file's second line names the original node. At the close, the registry write gives the node the new name and description (SKILL.md, *Registry write*). The ID is what every step finds the node by, so it never changes once a node has it.

## The law or regulation question

The last question of Part 2. Skipped in personal life (`Governing regime: None`). An earlier answer is recorded, not asked again.

**Ask:** "Is there a law or regulation that governs this work?"
- *Why:* Regulated steps are followed exactly, and a person approves the decisions the rules cover.
- *Example:* Financial-advice rules, health-privacy law such as HIPAA, or data-protection law such as GDPR.
- *Not sure?* Say not sure; I'll note it for you to check.

On a yes, in its own message, **Ask:** "Which one? A name or a description is fine." Then say: "Because this work is regulated, we'll note which steps and decisions the rules cover."

Record it for Security, Privacy & Safety as one line: `Governing regime: [name]`, `Governing regime: None`, or `Governing regime: Not sure — to check` (a "not sure", or a yes whose name stays unknown).

- **A yes,** even with the name unknown, switches on Part 4's detail table and its two regulation questions. On the light track, a yes or a "not sure" is a sign of risk (N-L2, SKILL.md).
- **"Not sure"** switches on neither on the full track; Design confirms with the leader before it lets the AI decide on its own.
