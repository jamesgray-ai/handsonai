# Part 1: What this is worth

Read when Part 1 starts, right after its signpost. Every quoted line is said exactly; each question is its own message.

Say first: "Before anything else, I want to know what this is worth to you, so that when it's built we can show the improvement rather than just claim it."

Settle four of the five `Value & Measurement` fields here, in three or four short messages, one question each, in this order: the objective (asked only when one is pre-loaded), the Desired Outcome (drafted for the leader to correct), the Measure and the Baseline. The Target comes at the end of Part 5, since it describes the workflow once it's running.

## 1. Business Objective

Which strategic objective this supports. Ask only when something is pre-loaded:

- **A Business node's `## Objectives`:** list them, then **Ask:** "Which of these does this workflow serve?"
- **The candidate already carries an objective:** ask this instead, never both in one message: **Ask:** "Your Analyze report tied this workflow to [objective]. Is that right, or is it the other one?" (with three or more objectives listed, "…or is it another one?").
- **The candidate's value is Analyze's fallback** ("None of the stated objectives — protects …"): the list question, without naming it.

A personal objective the leader offers instead ("get my Fridays back") still wins. With nothing pre-loaded, ask nothing: record the objective from the leader's description or document where it names one, otherwise "—". On the Individual lens it may be personal; don't push organizational language onto it.

## 2. Desired Outcome

What changes, and for whom, in the language the business uses. Never ask it open: draft it from what's known (the backlog card, the cold-entry answer, the leader's document), tag it (*(you said)*, *(from your [document])* or *(my suggestion)*), and play it back in one line that names what gets better and who notices, ending "What would you change or clarify?" (for illustration only: "Customers get their delivery date the same day, so fewer of them call to chase *(my suggestion)*. What would you change or clarify?"). The rubber-stamp guard applies to it. Value can be quality or risk, not only time saved: "better calls mean more proposals accepted" is a valid value.

## 3. Measure

What gets counted (cycle time, error rate, hours, volume, rework). It quantifies the Desired Outcome and never replaces it, and it counts only what this workflow moves directly: a broader business effect stays in the Desired Outcome as the reason, never a Measure. Confirm it, never ask it cold:

- **An Organizational candidate's `Success Metrics`,** played back only where this workflow moves them directly: **Ask:** "Your Analyze report suggested [measures]. Is that what we should count?"
- **Otherwise,** a measure you propose: **Ask:** "To show it worked, I'd count [measure]. Is that what we should count?"
- *Why:* Count what this workflow changes directly, so you can tell whether it worked.
- *Not sure?* Say yes. You can change it later.

**The value lever frames the proposal** when the candidate carries a `Value lever` and no `Success Metrics`: *Streamline*, steps or hours per run; *Automate*, the hours a person stops spending; *Accelerate*, cycle time or throughput; *Create value*, a count of the new thing produced. With no lever (cold entry), propose from the Desired Outcome and the work as described. `Success Metrics`, when present, win, and the lever only shapes the wording.

## 4. Baseline

Today's number for the Measure. Always ask it: Analyze doesn't capture it, and a number in the opportunity report isn't a baseline the leader has confirmed.

**Ask:** "What's [the measure, in plain words] today?" ("What's the time each report takes today?")
- *Not sure?* Say you don't know. Leaving it unknown is fine.

Read how it was got from the answer; never ask it. `Measured` when the leader names where the number comes from (a report, a log, a count); `Estimated` otherwise; `Unknown` when they don't know, which a "not sure" records at once (with no number, the row reads `— · Unknown`). Never push past `Unknown`, and never offer an estimate to fill the gap: an invented baseline makes a false improvement provable.

## An aim

An aim the leader states here ("same day") is noted for the target question at the end of Part 5.
