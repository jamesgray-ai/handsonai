# Part 5: Rules, where you check or approve its work, the sources it uses, and how you'll judge it

Read when Part 5 starts, right after its signpost, together with the requirements template (which holds what goes in each draft message). Purpose: close the gaps, mostly by reacting to a draft. Every quoted line is said exactly; each question is its own message. In a personal-life registry, the personal-life wording replaces the live-writes question; the taking-part and when-unsure questions use the same wording.

## Always asked, never drafted (before the drafts)

**1. Live writes.** When steps carry `writes` tags, a confirmation, listing them in plain words:

**Ask:** "It writes to: [list]. Anything else?"

With no `writes` tags:

**Ask:** "Does this workflow write to anything live — send, post, create, or change something in a real system?"
- *Why:* Anything it changes in the outside world needs a guard. Design checks each one.
- *Not sure?* If it only drafts for you to send, say no.

(The *Why* and *Not sure?* go with whichever form is asked.) For a write named here for the first time, in its own message, **Ask:** "Which step does that?"

**2. Taking part while it runs.**

**Ask:** "While it runs, do you want to take part, like reviewing a draft, answering its questions or approving something, or should it run start to finish without you?"
- *Why:* If it runs without you, it can't stop to ask, so it needs clear rules for when it's unsure.

Record at the top of Human Gates: `Runs: with you` or `Runs: without you`.

- If the student says "without you" but has named a review or approval point, point out the conflict: **Ask:** "You said it should run without you, but you also want to approve [point]. Which one holds?" If a gate the student performs (`(you)`) is still kept in the Part 5 draft after "without you", ask it again; if the student keeps the gate, the line becomes `Runs: with you`.
- A gate someone else performs (a controller) leaves `Runs:` as answered.
- If the answer names an approval point that matches no Human Gates row, add one, tagged *(you said)*; if its step is unclear, in its own message, **Ask:** "Which step does that come after?"

The send-back reason is not asked again: the third draft message plays the (must) checks back.

**3. When it's unsure.** Asked once:

**Ask:** "When it hits a case it can't confidently handle — stop and ask you, do its best and flag it, or skip that item?" If it runs without you, leave "stop and ask you" out of the choices.
- *Why:* This becomes a rule the workflow follows every time a case doesn't fit.
- *Not sure?* Do its best and flag it. You can change it after testing.

Record it as the Fallback row in Rules & Constraints. "Stop and ask you" also adds a Human Gates row.

## The draft, in four short messages

What goes in each, including message 4's test-input rules and its Hand-it-back text, is in the requirements template. Every line is tagged *(you said)* or *(my suggestion)*; each suggestion needs an explicit keep or drop (the rubber-stamp guard in SKILL.md), so the requirements stay the student's.

1. **Rules and never-dos**, ending "What's wrong or missing?"
2. **The human gates collected so far**, to confirm (no new gate questions), **and the sources it uses** (introduced the first time with the context sentence) and the Inputs, ending "What's wrong or missing?". The privacy questions come right after it.
3. **How you'll judge it**: the checks from Part 3 plus the quality standards held from Part 4, ending "What's wrong or missing?"
4. **The inputs Test will run**, ending with the Hand-it-back message.

## Then close Value & Measurement

Each in its own message:

**Ask:** "Now that we've reshaped this — what should the number be? What's the target?"
- *Why:* This is how you'll know whether the workflow paid off.
- *Example:* a bookkeeper might say: "Month-end close in two days instead of five."

**Ask:** "How long after this goes live before that number can actually be read?"
- *Not sure?* Say a month; you can change it.

These wait until now because a target describes the revised workflow.

## Then the labels preview (always)

Right after the Readable When answer (or its default), and before writing anything, show the labels preview (requirements template, section 3) in its own message: the report card Test will fill in, which introduces the labels AC, R and G. Never skip it, even when the interview ran long.
