# Part 5: Rules, sources and test cases

Read when Part 5 starts, right after its signpost; SKILL.md loads the requirements template at the same moment (it holds what goes in each draft message). Say first: "Last part: I'll draft the rules it follows, where you check its work, the sources it uses and the cases we'll test it on. You correct each one." Purpose: close the gaps, mostly by reacting to a draft. Every quoted line is said exactly; each question is its own message. In a personal-life registry, the personal-life wording replaces the live-writes question; the taking-part and when-unsure questions use the same wording.

## Always asked, never drafted (before the drafts)

**1. Live writes.** When steps carry `writes` tags, a confirmation, listing them in plain words:

**Ask:** "It writes to: [list]. Anything else?"

With no `writes` tags, say what's known and ask only the open part. When the student sends it themselves (a `(you)` send step or M line): **Ask:** "You send it yourself. Will the AI save the draft anywhere, such as in your email?" Otherwise: **Ask:** "Will it send or change anything itself, or only prepare drafts for you? Saving a draft in your email counts — tell me where."
- *Why:* Anything it changes outside this conversation is checked before it's built, and gets a limit that fits the risk.

(The *Why* goes with whichever form is asked first.) A saved draft is a write: record it with its action (`save as a draft`). When the student says it never sends, acknowledge that in one line and offer "never sends" as a Prohibited action in the first draft message. For a write named here for the first time, propose where it happens: "That's after step [N], once [x], right?", or with no steps, "That's after [moment], right?" The Writes line names that step or moment.

**2. Taking part while it runs.** When the student's own `(you)` checkpoint, step or M line already settles it, say: "You review every [deliverable] before it's sent, so this runs with you." (name what they do). Only when nothing settles it:

**Ask:** "While it runs, do you want to take part, like reviewing a draft, answering its questions or approving something, or should it run from start to finish without you?"
- *Why:* If it runs without you, it can't stop to ask, so it needs clear rules for when it's unsure.

Record at the top of Human Gates: `Runs: with you` or `Runs: without you`.

- If the student says "without you" but has named a review or approval point, point out the conflict: **Ask:** "You said it should run without you, but you also want to approve [point]. Which one holds?" If a gate the student performs (`(you)`) is still kept in the Part 5 draft after "without you", ask it again; if the student keeps the gate, the line becomes `Runs: with you`.
- A gate someone else performs (a controller) leaves `Runs:` as answered.
- If the answer names an approval point that matches no Human Gates row, add one, tagged *(you said)*; if its step is unclear, in its own message, **Ask:** "Which step does that come after?"

The send-back reason is not asked again: the third draft message plays the must-haves back.

**3. When it's unsure.** Asked once, even when the student said something like it earlier: an answer about one case isn't the rule for every case.

**Ask:** "When it hits a case it can't confidently handle — for example, [the student's tricky case] — should it stop and ask you, or do its best and flag it?" Add "or skip that item" only when one run handles several items (a batch of emails, a list of leads). If it runs without you, leave "stop and ask you" out of the choices; when that leaves one choice, say instead: "Since it runs without you, when it isn't sure it'll do its best and flag it for you."
- *Why:* This becomes a rule the workflow follows every time a case doesn't fit.
- *Not sure?* Do its best and flag it. You can change it after testing.

Record it as the Fallback row in Rules & Constraints. "Stop and ask you" also adds a Human Gates row. Where a flag goes is part of the rule: never inside the deliverable unless it's unmistakable and removed before sending. When only the student reads the deliverable (a pre-call brief), stating plainly what wasn't found ("No recent news found") is content for its reader, not a note.

## The draft, in four short messages (five when a security test trips)

Never say how many drafts are coming ("the first of four"): the count changes with the security limits, and the opening line already says what's coming. What goes in each, including message 4's practice-run rules, is in the requirements template SKILL.md loaded for this part. A draft message holds no ask of its own besides its ending (never "Name the place for each one"): a gap stays in the draft as a *(my suggestion)* or an unknown for the student to correct. Every line is tagged *(you said)* or *(my suggestion)*; each suggestion needs an explicit keep or drop (the rubber-stamp guard in SKILL.md), so the requirements stay the student's. Each requirement lives in one place: behaviours in message 1, qualities of the output in message 3.

1. **Rules and never-dos**, ending "What would you change or add?"
2. **The checkpoints collected so far**, to confirm (no new checkpoint questions), **and the sources it uses** (introduced the first time with the context sentence) and the Inputs, ending "What would you change or add?". The privacy questions come right after it.
   - **Only when a sensitivity test trips: the security limits**, its own short message after the privacy questions, ending "What would you change or add?". It is not numbered, so messages 3 and 4 keep their numbers.
3. **What every [deliverable] must get right**: the list from Part 3 plus the quality standards held from Part 4, ending "What would you change or add?"
4. **The practice runs**, opened and ended as the template says.

## Then close Value & Measurement

Each in its own message:

When the student stated an aim in Part 1: **Ask:** "In Part 1 you said [aim]. Is that the target, and what about [the other kept measure]?" With no aim, one per kept measure: **Ask:** "What should [measure] be once this is running?"
- *Why:* This is how you'll know whether the workflow paid off.
- *Example:* a bookkeeper might say: "Month-end close in two days instead of five."

**Ask:** "How long should it run before you check whether it's hitting those targets?"
- *Why:* That's when the runs so far can show whether it paid off.
- *Not sure?* Say a month; you can change it.

These wait until now because a target describes the revised workflow.
