# A change to a live workflow, and an older version's copy

Read, before anything changes, on every Build run that changes a live workflow (a small change, fix mode, a rebuild after a big or platform change, a requirement change from Test, a kept or undone direct edit, a put-back), on an install that replaces an earlier-version workflow that is live or was built, on a retired workflow's put-back, on running work brought in (the requirements carry a `Runs today` row that says where it's set up or that it's done by hand; one ending `· where: not asked` is Deconstruct's flag, and N-B51 handles it, `setup.md` section 6), whenever `schedule:` isn't `none` before go-live, when a schedule safety point fails on a live schedule, and for the copy of an older version after a yes to N-B51. Only the leader pauses, switches off or switches on a version that runs: give the steps, wait for their word, and never say you did it.

**Contents:** 1. The leader's pause, first · 2. The kept copy, next · 3. Running work brought in · 4. The change · 5. The close · 6. An older version's copy · 7. A shared skill other live workflows use

## 1. The leader's pause, first

Ask first, before any Part 1 item (at a first entry, as the opening's first action, `SKILL.md` entry check 6), on every Build run that changes a live workflow, replaces a live or built earlier version, or puts back a retired workflow, **whatever `schedule:` says** (a leader can schedule a workflow whose plan has no `SCH` task, and no step can see it). Before go-live, ask whenever `schedule:` isn't `none`. Said exactly (N-B41), in the form that fits the record, as a paragraph of its own starting on the form's own first word ("If"): the condition and the reason come first, and the reply most leaders give ("no schedule", or "yes") comes first among the replies; no lead-in in its sentence ("Before I change anything, please pause…" is a reworded line); anything you need to say first goes in the resume line or orientation line before it:

- **`schedule: paused` set since the last go-live** (a fix to the same change), checked first: it takes the place of every form below, switch-on steps or not: **Ask:** "If [workflow]'s schedule is still paused from the last change, keep it that way, so a scheduled run doesn't use the new version before it's tested. Say 'yes' if it's still paused, or pause it now[ ([steps])] and say 'done'." (the steps only when the record has your switch-on steps).
- **Switch-on steps in the record:** "If [workflow] runs on a schedule, pause it while I change it, so a scheduled run doesn't use the new version before it's tested: [steps]. Say 'no schedule' if it doesn't, or 'done' once it's paused."
- **Before go-live, with `schedule: not-on`:** "If you've switched on [workflow]'s schedule, pause it while I change it, so a scheduled run doesn't use the new version before it's tested: [steps]. Say 'no schedule' if you haven't, or 'done' once it's paused."
- **No switch-on steps in the record** (a schedule the leader made by hand, or a plan with no `SCH` task): "If [workflow] runs on a schedule you set up yourself, pause it while I change it, so a scheduled run doesn't use the new version before it's tested. Say 'no schedule' if it doesn't, or 'done' once it's paused."

Wait for "done" (or "yes" to the still-paused form), then write `schedule: paused`. "No schedule" leaves the value as it is. If the leader won't pause it, say exactly (N-B47): "I can't change [workflow] while its schedule is on: a scheduled run could use the changed version before it's been tested. Pause it with [steps], then say 'done'; or say 'stop' and I'll leave it as it is." (N-B47) (the whole line, its [steps] one clause, as in N-B41: never split into new sentences). Wait; on "stop", end without changing anything (a stop, not a close). The stop line for a "stop" here, at N-B48 or at N-B51's pause forms: one line (model wording) saying nothing was changed and what still waits, then N-F10's form for this platform with Build's phrase, last, with nothing after it. Before go-live with `schedule: none`, ask nothing.

## 2. The kept copy, next

Where files can be kept, save a copy of the current version in `history/kept-copy-YYYY-MM-DD-HHMM/`. Where the folder is a Git repository (`git rev-parse --show-toplevel` returns the workspace) and the installed paths have no changes since their last commit, that commit is the copy and nothing is copied; say so in one line (model wording). Never make a Git commit yourself here: a commit happens only through the Git offer, which asks first (`package-and-install.md`). Where the copy you keep in `built/` (in a folder built before this release, `package/` or `history/built-…/`) is there, copy it into `history/kept-copy-YYYY-MM-DD-HHMM/` yourself, asking nothing; ask only for a part it doesn't hold (N-B42): **Ask:** "Do you have a copy of [the part] as it is now? If not, copy it out now: [steps]. Paste it here, or say 'done' when it's saved with your build record." (N-B42) A pasted copy you save in `history/kept-copy-YYYY-MM-DD-HHMM/`. Write the steps to put the kept copy back in the record's "Put back the kept copy" section.

**An earlier version Build owns, or running work brought in** (section 3): N-B42 isn't asked, since its copy was never in `built/`; what you can't copy yourself gets the no-copy line below.

**With no copy,** don't change the workflow; say exactly (N-B48): "I won't change [workflow] until you have a copy of the current version, so you can go back if the change goes wrong. [Steps to keep one on this platform.] Say 'done' when you have it, or 'stop' to leave it as it is." (N-B48)

**An agent on Microsoft 365:** the record's last pasted instructions are the copy when N-E1's agent form said nothing changed (`microsoft-365-agent.md` section 6); otherwise the line above, with Agent Builder's steps to copy its instructions out.

## 3. Running work brought in

## 6. An older version's copy

After a yes to N-B51 (or something you found at an install name or place, or an "already there" at the install line), once the leader has paused it: a copy only where the new version will be saved over the older one (a part of the same name or in the same place). Anywhere else nothing of the older version is touched, so the paused version is its own copy, and none is asked for. Where a copy is needed, in this order:

1. **On Claude Code and Codex, already in Git.** Check yourself whether the older version's files are committed and unchanged since (`git status` and `git log` on those files). If they are, that commit is the copy; say so in one line (model wording).
2. **You make it,** where you can reach the files (a skill folder in the workspace, Cowork's skills folder, files in a drive you can write): into `history/kept-copy-YYYY-MM-DD-HHMM/`, saying where in one line (model wording). Nothing is asked.
3. **Only where you can't reach the files** (a skill kept in a Claude or ChatGPT account), ask once (N-B48's history question): **Ask:** "Before I save the new version over your older one: are its files saved in GitHub or another version history?" A yes counts as the copy.
4. **The leader keeps one:** after a no, say exactly (N-B48's older-version form), and wait: "I won't save the new version over your older one until you have a copy of it, so you can go back to it. [Steps to keep one on that platform.] Say 'done' when you have it, 'no copy' and I'll install the new one under a different name so nothing is overwritten, or 'stop' to leave everything as it is." "Done" is the copy. "No copy" is never a dead end: install the new part under a different name, record that as a ruling, and say the new name in one line (model wording). The new name goes everywhere the old one would have, the start phrase in "What was built" included (one that names the new part: the old phrase would start the older version too): decided in Part 1, the parts are built with it; decided at Part 3's install, change the orchestrator's references to that part, and the start phrase in "What was built" to one that names the new part (the old phrase would start the older version too), and run the built-text check again on what changed before that part is saved. The older version stays as it is, paused, and its line names it as still set up.

"Stop" at the pause form or here ends Build with nothing installed (a stop); the next entry asks again. Then write the older-version line (`build-record-template.md`), and, where a copy was kept, the steps to put the older version back in "Put back the kept copy". `schedule:` isn't touched: it belongs to the new workflow.

Where a new part takes the older version's place, it's installed over it when it's installed (in Part 3, with the install line's replace steps, ending by switching the skill on again where the leader switched it off). Then rewrite the older-version line in its replaced form, naming whatever of the older version is still set up, never the new part's place.
