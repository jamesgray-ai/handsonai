# Entry checks that are rarely needed

Read at entry when one applies: an earlier version Build owns (state 1), a record set aside, three rounds in a row not ready, or any installed part to rebuild or reinstall (the direct-edit check). Section names in italics are SKILL.md's; the numbers are SKILL.md's entry checks.

## An earlier version Build owns

**An earlier version Build owns** (`routing-rare.md`, *Earlier versions*: a `test-results.md`, no `build-record.md`, no `history/set-aside-*/`): N-B44 first when it's live or was built, then move the results files into `history/earlier-version-[date]/`, say so in one line (model wording; after N-B44 its first sentence already did), and build as for a new workflow. When the old one is live or was built, Part 3's install replaces it, so `references/live-change.md` applies before anything changes: its schedule is paused from this entry (entry check 6) and stays paused until Test takes the new one live, and N-B42 isn't asked, since its copy was never in `package/`.

## Entry check 4: a record set aside

**A record set aside** (a big change, or a platform or mechanism change): start a new record at once (`references/build-record-template.md`) and carry over from the newest set-aside record: the quick real checks done, `skills_on`, `write_block`, `schedule:`, any undo still outstanding, the "Live since" and "How to switch it off" lines, the older-version line, and, when the platform is unchanged, the row for the workflow's place (so N-B4's set-up clause, N-B17 and N-B40 aren't asked again). Keep only what still holds: a carried quick real check or block applies only to the same system in the same account. The set-aside record's `write_block` and `run_folders` always carry over, so nothing it left behind is forgotten: after a platform change, lift and clear them at entry (`references/claude-code-block.md` section 9). A set-aside record with no `schedule:`, or a set-aside folder with no record, counts as not `none`; a first build with no set-aside starts at `none`. Never move a record Design already set aside.

## Entry check 5: three rounds in a row not ready

**Three rounds in a row not ready** (counted from `test-results.md` and `history/test-results-round-*.md`, skipping `history/set-aside-*/`, `history/earlier-version-*/` and any round marked `round_status: abandoned`): N-B10 first, before fix mode's opener (`references/fix-mode.md` section 1; the opener only if the leader insists on fixing), unless the plan's `changes:` already logs a Build request whose `after_round` is the last round's number.

## Entry check 7: a direct edit

**A direct edit,** before you rebuild or reinstall any installed part (nothing installed yet, a first build: nothing to compare and no question). Where you can read the installed part and the runtime copies of its context files, compare them with the record's `fingerprints`. Where you can't (on Microsoft 365, always for an agent Agent Builder made), ask once in this entry: **Ask:** "Have you edited the workflow's instructions or its files directly since it was built?" Only the runtime context copies unreadable: **Ask:** "Have you edited the files your workflow reads ([the files, in plain words]) directly since it was built?" An agent Agent Builder made: **Ask:** "Apart from pasting the prompts I wrote, have you changed [Agent] in Agent Builder, or its Knowledge, since it was made?" On a yes, say "Paste [the instructions / the file] as [they are / it is] now, so I can match your requirements and plan to [them / it]. [How to copy it out on this platform.]" Then, for an edit found, before anything changes:
   - **Any other edit:** **Ask:** "I'll record that as a change so your requirements and plan match. OK, or should I put back the built version?" Keep (the recommended default): record a change request (`source: direct edit`, its `id` the next `B[n]`; the edited text saved as `history/direct-edit-[id]-YYYY-MM-DD-HHMM.md`, and `what` a one-line summary, in double quotes, naming that file: the text itself never goes in the frontmatter); the tasks it touches and their dependants wait, you finish the rest, and stop with N-B9 giving the edit the leader is keeping as the reason. Put back: reinstall the built version of that part (`references/fix-mode.md`, *Putting back the built version*) and carry on.
   - **An edit Design already declined** (its text matches the edited text saved in the file the `what` of a `direct edit` entry names, an entry with a `declined:` outcome in the plan's `changes:`): **Ask:** "That edit changes [the fixed step, in plain words], which your [rules require / policy requires], so it can't be kept. Shall I put back the built version?" (said whole: [the fixed step] is the fixed step the `declined:` reason names, as the requirements' Path describes it, in a short plain noun phrase; never a step or rule the reason doesn't name, and never a guess at why the edit was declined. Any explanation goes before the line, never in place of its words). A yes reinstalls and carries on. On a no, change nothing, say "Then I'll leave it as it is. While that edit is installed, I can't [test / build / change] [workflow]. When you want the built version back, say '[this step's start phrase]. My files are in [location].'" and stop (a stop), raising no request.
   - A part a logged put-back or `direct_edit: undo` touches is skipped (it's being put back anyway); a part that's no longer installed is never an edit: the rebuild or reinstall puts it back.
