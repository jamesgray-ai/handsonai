# The brief, the platform's creator, and the check before saving

Read before you build any skill or agent (Part 2, step 3), in fix mode, and for a live change. The platform builds every part with its own native way of making it; you write the brief, check what it made against the plan before anything is saved or used, and record it. You write a part yourself only where the platform has no native way to make it. On Claude and ChatGPT the skill creator is you: you load the platform's `skill-creator` and follow it yourself, in the same reply as the brief. Nobody else answers the brief in a later turn, so there's no one to wait for or to ask.

**Contents:** 1. Who builds, per platform · 2. The brief · 3. Before the creator starts · 4. While the creator works · 5. The check before saving · 6. The kept copy · 7. Saving, in Part 3 · 8. Schedules and connections

## 1. Who builds, per platform

Every part gets the same two guardrails, whoever builds it: any test its builder runs is a practice run, after N-F4's Build form where it applies (on Claude Code the builder runs no tests at all: section 4); and its text (instructions, tools, name and description) is checked against the plan, the practice-run lines word for word, before it's saved or used.

## 2. The brief

One brief per part, written from the plan's task and its blueprint, as one fenced block in the chat (on Claude and ChatGPT it's shown to the leader, in your own message text, introduced by one line *(your words)*, "Here's what I'm asking the skill creator to make:", before any of the creator's steps: never only in a file or a tool call; it's also your own source as you follow the skill creator), its first line `Skill brief: [part name]` (an agent's: `Agent brief: [part name]`), then these labelled parts:

- **What it does:** one or two sentences, from the blueprint.
- **Description:** the description it's saved with (what it does and when to use it), from the blueprint.
- **Steps:** the steps in order, with each checkpoint where it stops for the person.
- **Rules:** every check, rule, limit and Never line it carries, in the requirements' wording (`carried-lines.md` section 3). A rule tagged ` · (you)` or ` · ([role])` is that person's: it's never in the brief as the AI's rule.
- **Output structure:** the output's form and structure from the requirements' `## Output`, and how it's delivered from the plan's `Delivered as:` line (shown in the chat, a draft in [system], or a file in [place]; an older plan without the line: shown in the chat, unless a write delivers it). This is its one copy: it goes into the skill itself, and `context/` keeps no copy of it.
- **Tools:** for an agent, the tools it may use, reads only where the plan allows no change.
- **Uses skills from other plugins:** each skill the blueprint's `Uses skills from:` line names, as "[skill] from the [plugin] plugin", and the same in the record's `uses_skills:` (`{plugin, skill}`), written with the task's row. Left out when there's none.
- **Kept from the earlier version** (an extension): each item the leader kept (`SKILL.md`, *Phase 2*, step 3), in its own words; a dropped item is named here as "leave out: [item]".
- **Keep these exactly:** each line below quoted in full, word for word, one to a line, copied from `carried-lines.md` (never a pointer such as "the practice-run lines, as written in the skill text": the brief holds the lines themselves): the practice-run lines (section 2: the cue, the fixed first line with "before anything you produce", the never-made rule in every part that changes something, the given-input rule, the closing block and "All results"), the outside-content and never-read lines (section 3), and the `KW` lines in this platform's form with the location filled in (section 4); then: "Keep these lines exactly as written. Test it only under the practice-run cue: start every test with 'practice run'. Never install or save it until I say it passed."
- On Claude Code, with the skill-creator plugin: add "Use only the plugin's steps for writing the skill. Run no tests of it at all: no test prompts, evals, benchmarks or description-optimising loops, and no subagents or `claude` sessions; I run every check." (its test loop starts general-purpose subagents and `claude -p` sessions from this unblocked session, outside the wrapper, where nothing blocks a change). With that line in it, leave out the brief's "Test it only under the practice-run cue" sentence: on Claude Code nothing the creator runs is a test.
- On Claude Code and Codex: add "Write it in `framework/[workflow-slug]/built/[part name]/`, nowhere else."

No IDs (requirement, task or line) in the brief: only the wording. The brief is the creator's whole source: never hand it the plan or the requirements files.

## 3. Before the creator starts

Once in each session that builds or checks a part, before the first brief and before any of the creator's work: N-F4's Build form, where it applies (`SKILL.md`, *Phase 2*), said word for word with only [platform] filled in, as a paragraph of its own. Then the first brief. On Claude and ChatGPT, go straight on in the same reply: load `skill-creator` and follow it from the brief (section 4).

## 4. While the creator works

- **On Claude and ChatGPT you are the creator.** Follow `skill-creator`'s steps yourself, from the brief alone: draft the skill's files in this chat's sandbox, then package it with its packaging step (the file the save card saves). Its steps never wait for an answer to the brief and never ask the leader anything. Never write as if someone else made, checked or fixed the part ("the creator has fixed it"): you did, and you say only what your own calls showed.
- **Its questions** are answered from the plan; the leader never sees them. A question the plan can't answer is a ruling or a change request (`SKILL.md`, step 4).
- **On Claude Code, no tests at all.** The skill-creator plugin's test loop (test prompts run by general-purpose subagents, `claude -p` baselines, its benchmark and description scripts) never runs: your check agents and the wrapper's check sessions replace it (`claude-code-block.md` section 6). When the plugin's steps reach its tests, skip them and go straight to the check before saving (section 5); never start one of them yourself to satisfy it (`SKILL.md`, rule 6). Say nothing to the leader about the creator's tests.
- **On Claude and ChatGPT its tests are your own practice runs,** after N-F4's Build form, each one started with "practice run". Where a `skill-creator` step says to test the draft on a sample prompt, run it only as a practice run: put "practice run" at its start yourself before it runs; never run the sample prompt as written without the cue, and never a test that could send, post or change something for real.
- **Its tests,** on the other platforms, its own way of checking, are welcome, under the cue only. The brief already tells it to start every test with "practice run", and your Deny line came first. Where you can see a test before it runs (Claude Code and Codex, or a creator that asks first), read it: a test without the cue never runs; tell the creator in the same chat to add the cue, and only then let it go on. On the chat platforms the creator may run a test inside its own turn, before you can read it: the brief's cue and the Deny line are what hold there. A test that ran without the cue anyway: say so in one line *(your words)*, naming what it showed or changed; a real change it made is listed and offered for undo with the quick real checks' changes (N-B33).
- **Nothing is saved or installed** while it works: not into the account, not where the platform loads skills or agents.

## 5. The check before saving

When the part is ready, read its final text: on Claude and ChatGPT, the file you're about to keep and have the leader save (the packaged skill's `SKILL.md` and its files, read from the package itself, such as with `unzip -p`, or the draft file on disk where nothing is packaged), read with a call in this same reply after the last time it was made; in the chat on Microsoft 365 (where you can't read it there, ask the leader to paste it back); the files in `built/[part name]/` on Claude Code and Codex. Never say what a file holds ("it holds the skill exactly as I checked it") unless a call in this reply read it. Check it against the plan with the built-text check (`carried-lines.md` section 7): every check, rule, step and checkpoint; the output's structure; its name and description; every Never line; the practice-run lines word for word; no IDs.

- **A gap:** on Claude and ChatGPT, redo the draft yourself with the missing or changed line word for word, package it again, and read the new package; elsewhere, ask the creator, in the same chat, to fix it, quoting the line word for word. Then check again. Up to three tries in all.
- **Still missing after three tries, for a practice-run line, a Never line or a line that names a law:** the part is `Failed check`. Nothing of it is saved: no save card is offered, the leader is never asked to save, upload or download it, and it gets no kept copy (section 6 is written only after this check passes). The fresh-chat run is skipped (`fresh_chat_run: "skipped: [why]"`, `fresh-chat-run.md` section 2), and the build stops there: no other task is built after it. Never `Built, misses` for these. Say in one line *(your words)* that [the part] couldn't be made to keep [the line, in plain words], so it isn't saved, then the stop as every stop ends (`SKILL.md`, *The end of the part, and every stop*), with N-F10's form for this platform and Build's phrase last.
- **Any other line still missing after three tries:** `SKILL.md`, *A check that fails*.
- **It passed:** write the text you read to the kept copy (section 6), unchanged, and go on to the part's other checks (`SKILL.md`, step 6).

## 6. The kept copy

One fixed place for every part, on every platform: `framework/[workflow-slug]/built/[part name]/` in the working folder. A skill's text is `built/[skill name]/SKILL.md` (with its supporting files beside it); an agent's is its file in that folder (`built/[agent name]/[agent name].md` on Claude and Claude Code, `.toml` on Codex); a Workspace Agent's instruction document is `built/[agent name]/instructions.md`; an agent on Microsoft 365 keeps its build prompt and fix prompts there (`microsoft-365-agent.md`). On Claude and ChatGPT you write it once the check passes, from the file you read (section 5); on Microsoft 365, from the text the creator showed; on Claude Code and Codex the creator drafts there.

It's what Part 3 saves, what fix mode and a live change start from, and what putting back the built version reinstalls (`fix-mode.md` section 4). Before a rebuild writes over it, a live change moves the current copy into `history/kept-copy-YYYY-MM-DD-HHMM/` (`live-change.md` section 2). A folder built before this release keeps its copy in `package/` or `history/built-*/`: read it there, and write the next copy in `built/`.

## 7. Saving, in Part 3

Every part is saved together in Part 3, once every task has passed its checks (`package-and-install.md` section 2):

- **Claude and ChatGPT:** the leader saves each part from the save card, after N-B12's already-there clause (said before the first save card). The card saves the file you packaged; where it's no longer the kept copy's text, package the kept copy again. **Name the card's button as the card shows it** *(your words)*: a new skill's card reads "Save skill", one that replaces a skill of the same name reads "Update"; never one for the other. **On a fix or an extension,** one line before the card *(your words)* says what this version changes, in plain words ("This version takes out the booking link."), so the leader knows what they're saving.
- **The card itself is checked before the leader saves** (Claude and ChatGPT): what the card saves is what the leader gets, and it can differ from the text you checked. In the reply that offers the save card, before the offer, read the file the card saves (the package in this chat's sandbox, such as with `unzip -p`), run the built-text check (`carried-lines.md` section 7) on it, and compare it with `built/[part name]/` line for line. Never tell the leader to save, upload or download a file, or say what it holds, until a call in that same reply has read it. Where you can't read it (ChatGPT, or a card whose file you can't open), ask the leader *(your words)* to paste the card's text here, from the card before they save where it shows its text, otherwise from the saved skill straight after saving and before anything runs it, and check that the same way. A difference blocks the save: package it again from the kept copy (on Claude and ChatGPT you do it yourself; it's redoing the draft) and read and check the new package, up to three tries in all; a practice-run line, a Never line or a line naming a law still different after three is `Failed check` (section 5). A paste made after saving that differs blocks every run of it instead: no fresh-chat run until the fixed card is saved over it with the replace steps and pasted back matching. The install line asks the leader to save only once the card matches.
- **Claude, one line:** say *(your words)* that Claude saves each skill (or agent) inside a plugin of its own, naming it, and record each plugin's name in the record's `plugins:` (Test reads them when it checks which skills a practice run used).
- **Claude Code and Codex:** after N-B57's yes, the creator (or you, with no creator) writes each part from `built/` where the platform loads it.
- **Microsoft 365:** Copilot's creator saves the skills in Cowork's skills folder; each agent by Agent Builder (`microsoft-365-agent.md`).

Then check what was saved, where you can read it (Claude Code, Codex, Cowork's skills folder): the built-text check again, since a platform can shorten a description or drop a line as it saves. On Claude and ChatGPT the card's check above is that check; N-B12's question then confirms it shows.

## 8. Schedules and connections

The platform's own scheduler and connection screens make them. Your part is the brief (what to set, in one sentence and a link to the platform's page in `platform-docs.json`) and the check that each is set as the plan says (`setup.md` section 2; `standard-tasks.md` for `SCH`).
